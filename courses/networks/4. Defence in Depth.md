#  Defence in Depth

Defence in depth is a layered security model based on the assumption that no single control provides complete protection against compromise. The concept originates from a military strategy in which multiple defensive lines are used to slow an advancing force, absorbing and delaying an attack rather than stopping it at a single point. The term was adapted to information security to describe an architecture in which several independent controls are placed between an attacker and a target asset.

The core assumption underlying the model is that any individual control can fail, whether through misconfiguration, an unpatched vulnerability, or a zero day. Rather than treating this as an exceptional case, defence in depth treats the eventual failure of outer controls as an expected event, and inner layers are designed to detect, slow, or contain an intrusion that has already passed an outer boundary. This changes the design objective from preventing all intrusions to limiting the impact of an intrusion that does occur, for example by restricting what an attacker who has reached one layer can access, exfiltrate, or modify in adjacent layers.

![Concentric Rings](https://lattice-walker.github.io/CipherOps/courses/networks/4illustrations/ConcentricRings.svg)

Each ring corresponds to a different point at which an attacker might operate during an intrusion, and a control effective at one layer does not necessarily provide any protection at another; for example, a perimeter firewall has no visibility into an application-layer injection vulnerability, and disk encryption provides no protection against an authenticated user abusing legitimate access.

- **Redundancy**: duplicating a control, for example deploying two firewalls in a high-availability pair, so that the failure of one instance does not remove the control entirely.
- **Diversity**: using different technologies, implementations, or vendors to perform a similar function, for example combining a signature-based intrusion detection system from one vendor with an anomaly-based system from another.

These benefits are not without cost. Additional layers increase architectural complexity, since each control introduces its own configuration state, logging format, and failure modes that must be understood by operational staff. Costs increase both in licensing or hardware and in the staff time required to maintain, tune, and monitor each additional control. Operational overhead also increases the likelihood of configuration drift between layers, where controls are updated inconsistently over time and no longer reflect a coherent policy.

For this reason, the coherence of the overall architecture, meaning whether layers are explicitly designed to complement one another and cover different attacker capabilities, is generally considered more significant than the total number of tools deployed. A set of controls purchased or deployed independently, without a shared threat model or documented rationale for each layer, is described as "tool stacking," and does not by itself constitute defence in depth if the layers overlap in what they detect while leaving other attacker techniques uncovered by any layer.

**Zero Trust** is a security model summarised by the phrase "never trust, always verify," which departs from earlier perimeter-based models in which a user or device located inside a defined network boundary, such as an internal LAN, was implicitly trusted and granted broad access once past the perimeter. 

The model is generally described through three principles. 
- First, explicit verification requires that every access request be authenticated and authorised based on all available signals, including user identity, device state, location, and the sensitivity of the resource requested, rather than being granted automatically based on network location.
- Second, least-privilege access limits each identity, whether human or machine, to only the resources and actions required for its function, reducing what can be reached if that identity is compromised.
- Third, the model operates under an assumption of breach, meaning that architecture and monitoring are designed as though an attacker may already have a foothold inside the network, rather than assuming the perimeter has successfully excluded all threats.

A central architectural shift associated with zero trust is the move from network location to identity as the primary basis for granting access: a request is evaluated according to which user or device is making it and under what conditions, rather than according to which network segment it originates from. Micro-segmentation, the division of a network into small, tightly controlled zones, often at the level of individual workloads or application tiers, is used to limit lateral movement, so that an attacker who compromises one system cannot freely reach others without triggering additional authentication or authorisation checks. Authentication and authorisation are treated as continuous processes, re-evaluated throughout a session as context changes (for example if a device's security posture changes), rather than checked only once at initial login.

Zero trust is complementary to defence in depth, since it can be implemented as one or more layers, for instance at the identity and micro-segmentation layers, within a broader layered architecture, rather than as a replacement for physical, network, or host-level controls. 

## 1 Applied Cryptography

### 1.1 Encryption

Symmetric encryption uses a single shared secret key for both encryption and decryption. Because the same operation is used in both directions and the underlying mathematical operations are comparatively simple, symmetric algorithms are computationally efficient and are used for bulk data encryption, such as encrypting entire disks, files, or network sessions once a shared key has been established.

Asymmetric encryption, also called public-key encryption, uses a mathematically related key pair: a public key that can be distributed openly and a private key that must remain secret. Data encrypted with the public key can only be decrypted with the corresponding private key, which allows two parties to communicate securely without having previously exchanged a shared secret. Asymmetric operations are computationally more expensive than symmetric operations, which is why asymmetric cryptography is typically used for key exchange and digital signatures rather than for encrypting large volumes of data directly; in practice, protocols such as TLS use asymmetric cryptography to establish a shared symmetric key, which is then used for the remainder of the session.

- **Advanced Encryption Standard**: a symmetric block cipher typically deployed with 128-bit or 256-bit keys;
- **RSA**: an asymmetric algorithm based on the difficulty of factoring large integers, typically deployed with key lengths of 2048 bits or higher;
- **Elliptic curve cryptography**: an asymmetric approach based on the algebraic structure of elliptic curves, which achieves a security level comparable to RSA using substantially shorter keys.

Encryption at rest protects data stored on persistent media, such as disks, databases, or backup volumes, against unauthorised access if that media is obtained by an attacker. Encryption in transit protects data while it moves across a network, typically implemented through protocols such as TLS, and addresses interception by an attacker positioned on the network path. End-to-end encryption ensures that data is encrypted at the originating endpoint and only decrypted at the final receiving endpoint, without being decrypted by any intermediate system, including the service provider carrying the traffic. 

Key management encompasses several distinct operations: generation of cryptographic keys using a sufficiently strong source of randomness; secure storage, often using dedicated hardware such as hardware security modules; periodic rotation, replacing keys at defined intervals to limit the impact of an undetected compromise; and revocation, invalidating a key before its scheduled expiry if it is known or suspected to have been compromised. Common weaknesses identified in cryptographic deployments include the use of weak or predictable keys generated from insufficient randomness, flawed implementations that introduce side channels or logic errors despite using a sound underlying algorithm, and continued reliance on deprecated algorithms such as DES, whose 56-bit key length is now considered too short, or RC4, which has documented statistical biases that allow practical attacks. Regulatory frameworks such as the General Data Protection Regulation and the Payment Card Industry Data Security Standard include requirements addressing the protection of personal and payment data, which have contributed to broader adoption of encryption for data at rest and in transit in regulated sectors.

### 1.2 Multi-Factor Authentication

Multi-factor authentication requires a user to present two or more independent factors before access is granted, rather than relying on a single factor such as a password. 
- **Knowledge**: something the user knows, such as a password or PIN;
- **Possession**: something the user has, such as a hardware token, smart card, or registered mobile device;
- **Inherence**: something the user is, such as a fingerprint, facial pattern, or other biometric characteristic. 

![Multi-factor authentication](https://lattice-walker.github.io/CipherOps/courses/networks/4illustrations/4MFA.svg)[
Common implementations include one-time passwords delivered by SMS or generated by a dedicated application, physical hardware tokens that generate or store cryptographic credentials, authenticator applications implementing time-based or counter-based one-time password algorithms, and biometric sensors integrated into devices.

The FIDO2 and WebAuthn standards are described as phishing-resistant because authentication is cryptographically bound to the specific origin (the domain requesting authentication), which prevents credentials from being replayed against a fraudulent site impersonating the legitimate service; unlike a password or a one-time code, the underlying private key never leaves the user's device and is not transmitted or displayed in a form that could be intercepted or entered into a phishing page.

## 2 Firewall

![Firewall](https://lattice-walker.github.io/CipherOps/courses/networks/1illustrations/1FIREWALL.svg)

A perimeter [firewall](https://lattice-walker.github.io/CipherOps/display_courses/courses.html#article=courses%2Fnetworks%2F1.%20Introduction.md) is positioned at the boundary between the internet and an organisation's internal network, filtering traffic entering or leaving that boundary. Internal segmentation firewalls are placed within the internal network itself, controlling traffic that moves between internal segments, as distinct from traffic crossing the organisational perimeter, internal segmentation limits how far an attacker who has compromised one internal segment can move without encountering an additional control point.

Firewalls may be configured with two network interfaces, described as dual-homed, typically separating two networks such as an internal network and the internet, or with more than two interfaces, described as multi-homed, allowing simultaneous separation of multiple network segments, such as an internal network, a demilitarised zone, and the internet, from a single device.

Firewalls are commonly used to define a demilitarised zone, a network segment that hosts systems intended to be reachable from untrusted networks, such as public web servers or mail relays, while remaining isolated from systems on the internal network that hold more sensitive data or functions. Placing such systems in a dedicated segment limits what an attacker can reach directly if one of those exposed systems is compromised.

High-availability configurations allow firewall functionality to continue if a device fails. In an active-passive configuration, a standby device takes over processing if the active device fails, while in an active-active configuration, multiple devices process traffic concurrently and share load, with failure of one device leaving the others to continue handling traffic. Firewall placement can introduce asymmetric routing, in which traffic belonging to a single connection follows different physical or logical paths in each direction; this can cause a stateful firewall to see only one direction of a connection, preventing it from establishing connection state correctly and causing legitimate traffic to be dropped, which must be accounted for in network design, for example by ensuring that both directions of traffic for a given connection traverse the same firewall.

## 3 Access Control Lists

An ACL is an ordered set of rules applied to a network interface or to a file system object, used to permit or deny specific traffic or specific access operations. Network ACLs filter traffic based on criteria such as source and destination IP address, source and destination port, and protocol.

In Cisco terminology, a standard ACL filters based on the source IP address alone, while an extended ACL can filter on a broader set of criteria, including destination address, port number, and protocol, allowing more granular control.

ACLs are generally stateless: unlike a stateful firewall, an ACL does not automatically track the state of a connection, so return traffic for a permitted outbound connection must be explicitly allowed by a separate rule if it is to be permitted in the reverse direction. Rules within an ACL are evaluated in the order in which they are defined, and processing stops at the first rule that matches a given packet(first-match logic) most implementations apply an implicit deny at the end of the list, meaning that any packet not matched by an explicit rule is dropped.

ACLs can be applied at different points in a network: 
- **on routers**, where they typically filter traffic based on Layer 3 and Layer 4 information as described above,
- **and on switches**, in the form of VLAN ACLs, which filter traffic within or between VLANs, or port ACLs, which filter traffic on a specific physical switch port.

### 3.1 Anti-Spoofing

IP spoofing refers to the practice of forging the source IP address field of a packet so that it appears to originate from a different host than the one that actually sent it. This technique can be used to bypass ACLs that rely on source address for authorisation, or to conceal the true origin of an attack from the target or from downstream monitoring systems.

![Ingress and Egress filtering](https://lattice-walker.github.io/CipherOps/courses/networks/4illustrations/4InEgress.svg)

Ingress filtering (such as [BCP38](http://www.bcp38.info/index.php/Main_Page)) is applied at a network boundary to block packets whose source address is inconsistent with the network segment from which they were received, for example blocking a packet arriving on an interface connected to a customer network if its source address does not fall within the range of addresses assigned to that customer. Egress filtering applies the same principle in the outbound direction, blocking packets leaving a network if their source address does not correspond to that network's assigned address space, preventing hosts within the network from sending spoofed traffic outward.

![Unicast Reverse Path Forwarding](https://lattice-walker.github.io/CipherOps/courses/networks/4illustrations/4URPF.svg)

Unicast Reverse Path Forwarding is a complementary mechanism, generally implemented on routers, that checks whether a route back to a packet's claimed source address would use the same interface on which the packet was actually received; if not, the packet is considered inconsistent with expected routing and is dropped. This provides similar protection to explicit ingress filtering but derives its decision from the routing table rather than from a manually configured list of expected addresses.

## 4 IDS and IPS

### 4.1 Intrusion Detection Systems

An intrusion detection system passively monitors network or host activity and generates alerts when it identifies activity matching its detection logic, without itself altering or blocking the traffic or activity observed. Network-based intrusion detection systems monitor traffic at defined points in the network, typically by receiving a copy of traffic through a mirrored switch port or a network tap, while host-based intrusion detection systems monitor activity occurring on an individual endpoint, such as file changes, process execution, or system calls.

Signature-based detection compares observed activity against a database of patterns associated with known attacks, generating an alert when a match occurs; this approach is effective against previously documented threats but has limited effectiveness against zero-day attacks, meaning attacks exploiting vulnerabilities or using techniques not yet represented in the signature database. Anomaly-based detection instead establishes a baseline of what is considered normal behaviour for a given network or host, and generates alerts when observed activity deviates significantly from that baseline, which can identify previously unseen attack techniques but is also more prone to flagging legitimate but unusual activity.

Detection systems must balance false positives, alerts generated in response to benign activity, against false negatives, genuine attacks that go undetected; adjusting detection thresholds and rules to manage this balance for a specific environment is referred to as tuning. Systems that generate a high volume of false positives without adequate tuning can lead to alert fatigue, a condition in which analysts, overwhelmed by the volume of alerts requiring review, become slower to respond to alerts or begin to disregard them, including alerts that represent genuine incidents. Commonly referenced open-source implementations of intrusion detection functionality include Snort and Suricata, both primarily network-based, and OSSEC, primarily host-based.

### 4.2 Intrusion Prevention Systems

An intrusion prevention system uses detection logic similar to that of an intrusion detection system, including both signature-based and anomaly-based methods, but is deployed inline within the traffic path, which allows it to block, drop, or modify traffic identified as malicious in real time rather than only generating an alert after the fact. The distinction between an intrusion detection system and an intrusion prevention system is therefore generally one of enforcement position rather than detection method.

Inline placement introduces additional latency into the traffic path, since each packet must be processed by the device before being forwarded, and introduces a potential point of failure: if the device fails or becomes overloaded, it can affect the availability of the traffic passing through it. Devices can be configured with a fail-open behaviour, in which traffic is allowed to pass unfiltered if the device fails, prioritising availability, or a fail-closed behaviour, in which traffic is blocked if the device fails, prioritising security at the cost of potential service disruption.

Evasion techniques used against intrusion prevention systems include fragmenting malicious content across multiple packets so that no single packet matches a detection signature, encoding content in a form not recognised by the detection logic, and exploiting ambiguity in how different systems interpret a given protocol, causing the intrusion prevention system and the target system to reach different conclusions about the content of the same traffic. Default rule sets provided with intrusion prevention systems are generally considered insufficient without tuning specific to the protocols, applications, and traffic patterns present in a given environment, since default configurations are designed to apply broadly rather than to any single deployment. Intrusion prevention systems are commonly integrated with firewalls, sometimes as a combined function within a next-generation firewall, and with security information and event management platforms, allowing their alerts and actions to be correlated with data from other sources.

### 4.3 Multi-Layer Detection Strategies

Correlation of events across these layers is typically performed using a security information and event management platform, which aggregates log and alert data from multiple sources and applies rules or analytics to identify patterns that would not be apparent from any single source in isolation, such as a failed login on one system followed shortly by a successful login from the same account on another system.

![Honeypot](https://lattice-walker.github.io/CipherOps/courses/networks/4illustrations/4honeypot.svg)

Deception technologies, including honeypots, individual decoy systems designed to appear as legitimate targets, and honeynets, networks of such decoy systems, are deployed to attract and detect attacker activity; because these systems have no legitimate business function, any interaction with them is treated as a strong indicator of malicious activity, generally with a low false positive rate compared with detection methods monitoring production systems. Threat intelligence feeds provide external context, such as indicators associated with known malicious infrastructure or campaigns, which can be used to enrich internally generated alerts, for example by flagging traffic to or from an IP address independently reported as associated with malicious activity. 

## 5 Logging, Monitoring and Intrusion Detection

Security logs typically cover authentication, network flows, system calls, and application errors. They are centralised via protocols like syslog and standardised into formats such as CEF or JSON for analysis.

Log integrity is protected through tamper-evident storage or cryptographic chaining, while retention is driven by regulation and storage cost. Normalisation makes heterogeneous logs comparable, though gaps remain: devices that can't log, filtered high-volume sources, and clock drift, all of which can hinder incident reconstruction.

This log data is of limited value without a function to continuously review it, which is the role of the Security Operations Center: a centralised team responsible for monitoring, detecting, and responding to security events across an organisation's systems and networks. Organisations may operate this function in-house, outsource it to a managed security service provider, or adopt a hybrid arrangement in which certain tasks, such as initial monitoring, are outsourced while others, such as incident response, are retained internally.

Core tooling built around the logging pipeline described above generally includes a security information and event management platform for aggregating and correlating collected logs; security orchestration, automation and response tools, which can automate routine investigation or response steps; ticketing systems, used to track alerts through to resolution; and threat intelligence platforms, which provide external context such as known indicators of compromise.

Staff are typically organised into tiers. First-line, or Tier 1, analysts perform initial triage of alerts generated from this log data, determining whether further investigation is warranted. Second-line, or Tier 2, analysts conduct deeper investigation of alerts escalated by the first tier. Third-line, or Tier 3, staff handle formal incident response for confirmed incidents and conduct proactive threat hunting, searching the same log sources for indicators of compromise not already flagged by automated detection.

## 6 VPN

![VPN](https://lattice-walker.github.io/CipherOps/courses/networks/4illustrations/4VPN.svg)

A Virtual Private Network establishes an encrypted tunnel across a network that is not otherwise trusted, such as the public internet, allowing traffic to be exchanged with a level of confidentiality and integrity comparable to a private, dedicated connection. A site-to-site configuration connects two fixed networks, for example the networks of two office locations, through a tunnel typically established between two gateway devices, without requiring configuration on individual end-user devices. A remote-access configuration instead connects an individual user's device directly to a corporate network, typically through client software running on that device.

IPsec is commonly used to implement VPN connections and operates in one of two modes: tunnel mode, in which an entire original packet, including its header, is encapsulated within a new packet, commonly used between gateways; and transport mode, in which only the payload of the original packet is protected while the original header remains visible, more commonly used for host-to-host communication. Key exchange for IPsec connections is negotiated using the Internet Key Exchange protocol, which establishes a shared key between the two endpoints without transmitting that key directly. Data is then protected using the Encapsulating Security Payload protocol, which provides confidentiality and integrity, or the Authentication Header protocol, which provides integrity and origin authentication without confidentiality.

TLS-based alternatives to IPsec include SSL VPN implementations, which establish a tunnel using the same protocol family used to secure web traffic; OpenVPN, an open-source implementation using TLS for key exchange; and WireGuard, a more recent implementation designed around a smaller codebase and a fixed set of modern cryptographic primitives.

Split tunnelling is a configuration in which only a defined subset of a user's traffic, typically traffic destined for the corporate network, is routed through the VPN tunnel, while other traffic, such as general internet browsing, is sent directly from the user's device without passing through the tunnel. This improves performance by avoiding unnecessary routing of unrelated traffic through the corporate network, but introduces a security implication: if the user's device is compromised through the unprotected, direct path, that compromise could potentially be used to reach the corporate network through the same device's VPN connection. Performance considerations relevant to VPN deployment include the processing overhead introduced by encryption and decryption of traffic, and issues related to the maximum transmission unit, since encapsulation adds overhead to each packet that can cause packets to exceed the maximum size supported along a given network path, requiring fragmentation.

VPN concentrators may terminate in the DMZ, allowing traffic to be inspected before reaching internal systems; placing VPN endpoints directly inside the internal network is generally seen as riskier. Because VPNs typically grant broad network-level access once connected, they are often paired with zero trust principles to add finer, per-resource authorisation.

## 7 Authentication and Network Access Control

### 7.1 RADIUS

[The Remote Authentication Dial-In User Service](https://en.wikipedia.org/wiki/RADIUS), is a client-server protocol used to centralise authentication, authorisation, and accounting functions across multiple network devices. In this context, authentication verifies a user's identity, authorisation determines what that user is permitted to do once authenticated, and accounting records information about the user's session, such as its duration, for auditing or billing purposes.

Network devices such as switches, wireless access points, or VPN gateways act as RADIUS clients, referred to as Network Access Servers in this context, forwarding authentication requests received from users or devices to a central RADIUS server rather than validating credentials locally on each device.

RADIUS is often compared with TACACS+, another protocol used for centralised authentication, particularly for administrative access to network devices. The two protocols differ in several respects, including their transport protocol and the granularity with which they separate authentication, authorisation, and accounting functions; TACACS+ is more commonly used specifically for controlling and auditing administrative access to network infrastructure devices, while RADIUS is more commonly used for network access authentication generally, including wireless and remote-access scenarios.

Extensible Authentication Protocol methods carried over RADIUS include EAP-TLS, which uses certificates on both the client and server for mutual authentication and is generally regarded as providing strong security at the cost of certificate management overhead; PEAP, which establishes a TLS tunnel to protect a subsequent, potentially weaker authentication method carried within it; and EAP-TTLS, which similarly establishes a protected tunnel but allows a broader range of inner authentication methods.

Known weaknesses in RADIUS include its reliance on an MD5-based mechanism to obscure the shared secret used to hide certain sensitive attributes within RADIUS packets, a mechanism that has been shown to be susceptible to offline attacks against captured traffic, since MD5 is no longer considered cryptographically strong. RADIUS over TLS, referred to as RadSec, addresses this weakness by encrypting the entire RADIUS session using TLS, rather than relying solely on the protocol's native, weaker attribute-hiding mechanism.

### 7.2 Network Access Control

[Network access control](https://en.wikipedia.org/wiki/Network_access_control) refers to mechanisms that enforce policy on devices either before they are granted access to a network, described as pre-admission control, or after initial access has been granted but before full access is confirmed, described as post-admission control. Posture assessment, a common component of network access control, evaluates a device's patch level, antivirus or endpoint protection status, and configuration compliance against a defined policy before granting or continuing network access.

802.1X is the standard mechanism for port-based access control, requiring a device connecting to a switch port or a wireless network to authenticate before being granted access to the network beyond that port. Devices that fail authentication or fail a posture assessment may be placed into a quarantine VLAN, a restricted network segment that isolates the device from the rest of the network, often providing only limited access, such as to remediation resources, until compliance is achieved.

Bring-your-own-device policies and Internet of Things devices present particular challenges for this model, since many such devices, particularly simpler embedded devices, cannot run the client software, referred to as a supplicant, required to perform 802.1X authentication; alternative mechanisms, such as authentication based on the device's MAC address, are sometimes used for such devices, though these provide weaker assurance than 802.1X. Network access control systems are commonly integrated with identity providers, to determine which user is associated with a given device or connection, and with endpoint management platforms, to obtain up-to-date information about a device's patch and configuration status for use in posture assessment.

### 7.3 Read-Only Domain Controller

[A read-only domain controller](https://www.thehacker.recipes/ad/movement/builtins/rodc) holds a copy of the Active Directory database that cannot be directly modified locally; instead, changes originate at a writable domain controller elsewhere in the environment and are replicated one-way to the read-only domain controller. This design is used in locations considered physically insecure or difficult to adequately secure, such as remote branch offices where the physical security controls available may not match those of a central data centre.

By default, a read-only domain controller caches the credentials only of accounts explicitly permitted to authenticate at that location, according to a defined password replication policy, rather than caching credentials for all domain accounts; this limits the potential impact if the physical server is stolen or otherwise compromised, since only a limited subset of credentials would be exposed.

The Filtered Attribute Set is a mechanism that defines which sensitive attributes, for example certain security-related attributes, are excluded from replication to any read-only domain controller, further limiting what could be exposed by a compromise of such a server. Administrator Role Separation allows a designated local user to perform administrative tasks on the read-only domain controller itself, such as managing local services, without that user being granted administrative privileges over the domain as a whole. Taken together, these features are described as reducing the attack surface presented by a read-only domain controller compared with a standard, writable domain controller placed in the same physically less secure location.

### 7.4 Bastion Host

A [bastion host](https://en.wikipedia.org/wiki/Bastion_host) is a hardened, publicly accessible system that provides controlled access to a private network, typically positioned so that administrative connections from outside the network must pass through it rather than reaching internal systems directly. Common uses include serving as an SSH jump host, through which administrators connect before reaching internal Linux or Unix systems; an RDP gateway, serving the equivalent function for Windows remote desktop connections; or a privileged access workstation, a dedicated, tightly controlled system used specifically for performing administrative tasks.

Hardening of a bastion host typically involves running a minimal set of services, so that the system exposes as few potential vulnerabilities as possible; applying strict access control, limiting which users and source addresses may connect to it; and maintaining comprehensive logging of all activity on the host, given its role as a chokepoint for administrative access.

Bastion hosts are sometimes described as a transitional architecture toward zero trust, since they centralise and constrain administrative access at a single point without necessarily applying the continuous, per-resource verification associated with a full zero trust model. A significant risk associated with this architecture is that the bastion host represents a single point through which a large proportion of administrative access flows; its compromise could grant an attacker access to any internal system reachable through it, and its unavailability could prevent legitimate administrators from performing necessary tasks. Privileged access management platforms, which centrally manage and audit the use of privileged credentials, and just-in-time access mechanisms, which grant temporary access for a limited duration rather than standing access, are described as modern alternatives or complements to a static bastion host, reducing the window during which administrative access is available and the scope of what a single compromised credential can reach.

## 8 Traffic Matrix and Service Identification

A traffic matrix is a structured mapping of expected communication flows between network segments or individual hosts, typically recording, for each flow, the source, destination, protocol, and port, along with a description of the application or service the flow supports. It provides a documented basis for defining firewall rules and ACLs that reflect actual, authorised communication requirements, and for establishing baselines against which anomalous or unexpected traffic can later be identified.

Data sources used to build a traffic matrix include network flow records, such as those in the NetFlow or IPFIX formats, which summarise communication between hosts without necessarily capturing full packet content; packet captures, which provide more detailed content where necessary; and documentation provided by application owners describing the expected communication requirements of their systems. Identifying which flows are authorised generally requires direct input from application owners and system administrators, since flow records alone indicate what traffic has occurred, not whether that traffic reflects an intended or approved design.

Flows observed in practice that are not documented in existing records require further investigation during a discovery phase, in which their purpose and legitimacy are established, before any decision is made about whether to formally authorise them or block them during a subsequent enforcement phase. Maintaining an accurate traffic matrix over time requires integration with an organisation's change management process, so that new systems or modified communication patterns are reflected in the matrix as they are introduced, rather than allowing the documented matrix to diverge from actual network behaviour.

The traffic matrix can also be used to validate existing firewall rule sets, comparing documented, authorised flows against configured rules to identify rules that do not correspond to any known or currently used flow, which may indicate rule bloat or the presence of undocumented, potentially unnecessary access.

## 9 Best Practices and Hardening

### 9.1 Oversizing and Backup

Capacity planning involves provisioning network bandwidth, processing capacity, and storage with headroom beyond typical or average demand, allowing systems to absorb unexpected spikes in legitimate traffic or to continue functioning, at least partially, under the elevated load associated with a denial-of-service condition. Redundant links and devices, meaning the deployment of more than one instance of a given network path or device, are used to remove single points of failure from network design, so that the failure of any one component does not result in a complete loss of connectivity or service.

Backup strategies commonly distinguish between full backups, which copy the entirety of the data being protected; incremental backups, which copy only the data that has changed since the most recent backup of any type, resulting in smaller and faster individual backups but requiring the full sequence of backups to restore; and differential backups, which copy all data changed since the last full backup, resulting in a compromise between backup size and restoration complexity compared with the other two approaches.

Backup storage may be located on-site, providing fast access for routine restoration but sharing physical risk with the production environment; off-site, at a separate physical location, protecting against site-level events such as fire or flood; or in a cloud service, offering off-site storage without the organisation needing to manage the physical infrastructure itself. Air-gapped backups, which are physically or logically isolated from the production network and cannot be reached by systems on that network, are used specifically to improve resilience against ransomware, since malware that encrypts or deletes data on connected systems and their accessible backups cannot reach backups that are not network-accessible at the time of an attack.

Recovery time objective defines the maximum acceptable duration of downtime following an incident before a system must be restored, while recovery point objective defines the maximum acceptable amount of data loss, measured as a period of time, between the most recent backup and the point of failure. Both are used as parameters when designing a backup and recovery strategy, since they determine the required frequency of backups and the acceptable methods and infrastructure for restoration. Regular restoration testing, meaning the practice of actually restoring data from backups on a periodic basis rather than only creating them, is necessary because a backup that has not been tested cannot be assumed to be recoverable; failures can occur due to corrupted backup files, incompatible restoration procedures, or missing dependencies that are only discovered when a restoration is actually attempted.

### 9.2 Update Server

Centralising patch distribution through an internal update server allows an organisation to avoid the need for individual managed hosts to access the internet directly to retrieve updates, reducing the number of systems with direct external connectivity and allowing updates to be reviewed before wider deployment. Common implementations include Windows Server Update Services for Windows environments, which allows an organisation to approve specific updates for internal distribution, and local package mirrors for Linux distributions, which host a local copy of a distribution's package repository for internal systems to use instead of the public repository.

Organisations typically control which updates are approved and deployed through a staged rollout process, in which a given update is first applied to a limited set of test systems, monitored for adverse effects, and only then approved for progressively wider deployment across the remaining managed systems. A compromised update server represents a supply chain risk, since it is trusted by a potentially large number of downstream systems that will install whatever it distributes; if an attacker gains control of the update server, that trust relationship can be used to distribute malicious software to all systems relying on it. For this reason, the update server itself must be kept patched and hardened to a standard at least equivalent to, and often exceeding, that of the systems it serves, given the scale of impact a compromise of this single system could produce. In air-gapped or operational technology environments, where systems are not connected to the internet, updates are typically transferred through controlled offline processes, such as physically transporting verified update files on removable media, rather than through direct network connectivity to a vendor's update infrastructure.

### 9.3 Discretionary Access Control

Discretionary access control is a model in which the owner of a given resource, such as a file, determines who may access that resource and what operations they may perform on it, with the owner generally free to grant or revoke access at their own discretion. This differs from mandatory access control, in which access decisions are determined by a centrally defined policy that individual resource owners cannot override, typically used in environments with strict, centrally enforced classification requirements; and from role-based access control, in which permissions are assigned according to a user's defined role within an organisation rather than being set individually by each resource owner.

Discretionary access control is implemented in common operating systems through mechanisms such as UNIX permission bits, which define read, write, and execute permissions for a file's owner, group, and other users, and the Windows discretionary ACL, which allows more granular permission assignment to individual users or groups. The principle of least privilege, granting a user only the access required to perform their assigned tasks and no more, is generally presented as the governing design rule when configuring permissions under this model, since the model itself places few inherent restrictions on how broadly an owner may choose to grant access.

Common misconfiguration patterns include overly permissive default settings, in which newly created resources are given broader access than necessary until an administrator or owner actively restricts them, and permission inheritance issues, in which a file or folder inherits permissions from a parent directory in a way not intended or reviewed by the resource owner, resulting in unintended access. Auditing and reviewing assigned permissions, using dedicated tools capable of reporting on effective access across a system or file share, is used to identify such issues, generally on a periodic basis defined by organisational policy.

A limitation of discretionary access control is its susceptibility to Trojan horse attacks, in which a program executed with a legitimate user's permissions performs unauthorised actions using that user's own access rights, since the model has no inherent mechanism to distinguish between access exercised intentionally by the user and access exercised by software acting on the user's behalf without their knowledge. The model's overall effectiveness is also described as dependent on the diligence of individual resource owners, since there is no central authority enforcing a consistent standard of care across all resources.
