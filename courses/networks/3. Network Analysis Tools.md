# 3. Network Analysis Tools
## 3.1 Wireshark
To learn more about this section, I highly recommend reading [Practical Packet Analysis, 3rd Edition : Using Wireshark to Solve Real-World Network Problems, by Chris Sanders](https://search.worldcat.org/fr/title/1047868641) and [WIRESHARK for Security Professionals : Using Wireshark and the Metasploit Framework, by Jessey Bullock and Jeff T. Parker](https://search.worldcat.org/fr/title/975223991)

Wireshark is a network packet capture and analysis tool, which operates at the level of individual frames, datagrams, packets, and segments, allowing detailed inspection of traffic at each layer of the network stack. 
It is best suited to targeted investigations: diagnosing the root cause of a network issue, locating traffic belonging to a specific protocol, or examining the timing of exchanges between hosts. 
It can also be used to identify the most active hosts on a network or to get a broad view of traffic composition. 
It is not, however, a general-purpose network discovery tool. 
Without a specific question in mind, browsing raw captures tends to produce more noise than insight, given the volume and variety of packets present on any active network.

### 3.1.1 The graphical user interface

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkUI.png)

Wireshark organises captured traffic across three panes displayed simultaneously. 
Each pane provides a different level of abstraction over the same underlying data, and understanding how they relate to one another is a prerequisite for efficient packet analysis.

The Packet List Pane occupies the top portion of the interface and presents one row per captured packet. 
Each row shows the source and destination addresses, the identified protocol, the frame length, and a summary in the Info column. 
This pane is the entry point for any analysis session: it gives an immediate sense of traffic composition and allows the analyst to select a packet for deeper inspection.

The Packet Details Pane, positioned in the middle, displays the selected packet as a hierarchical tree of collapsible subtrees. 
Each subtree corresponds to a layer of the OSI model. 
The first subtree, labelled "Frame", contains metadata added by Wireshark itself rather than data present on the wire: the packet number, the capture timestamp, 
the interface on which the frame was recorded, and the comparison between the captured length and the original length on the wire. 
Below it, successive subtrees represent the Ethernet header (Layer 2), the IP header (Layer 3), the transport layer header, typically TCP or UDP (Layer 4), 
and any application-layer protocol Wireshark has been able to identify (Layer 7). Each field within a subtree corresponds to a specific sequence of bytes in the raw frame.

The Packet Bytes Pane, at the bottom, exposes those raw bytes directly. It is structured in three columns. 
The leftmost column shows the offset of each row from the start of the packet, expressed in hexadecimal: a value of 0x0010, for instance, indicates that the row begins at the sixteenth byte. 
The middle column lists the hexadecimal value of each byte as it was captured on the wire. The rightmost column provides an ASCII interpretation of the same bytes, 
where printable characters are rendered as text and non-printable characters are replaced by a dot.

The three panes are not independent views: they are synchronised representations of the same data. 
Clicking on any field in the Packet Details Pane causes Wireshark to highlight the corresponding bytes in the Packet Bytes Pane. 
This correspondence is particularly useful when verifying how a dissector has parsed a given field, or when investigating a malformed packet where the dissector's 
interpretation may not match the actual byte sequence. Developing the habit of cross-referencing these two panes is one of the more reliable ways to build confidence in 
reading unfamiliar protocols.

### 3.1.2 Wireshark Filters

Wireshark provides two distinct filtering mechanisms, each operating at a different stage of the capture process and using a different syntax. 
Knowing which to apply, and when, is essential for keeping analysis manageable.

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/CaptureFilters.png)

Capture filters are applied before any packet is recorded. They instruct Wireshark to discard traffic that does not match the specified criteria, 
which directly reduces the size of the resulting pcap file. This makes them appropriate when the scope of the investigation is already well defined, 
for instance when only traffic to a specific host or port is relevant. Capture filters use Berkeley Packet Filter syntax, the same syntax used by tools such as tcpdump. 
A filter expression is built from three components: a protocol qualifier (such as `ether`, `tcp`, `ip`, `ip6`, or `arp`), a direction qualifier (`src` or `dst`), 
and a type qualifier (`host`, `port`, `net`, or `portrange`). These components can be combined using the logical operators `and`, `or`, and `not`. Special primitives 
such as `broadcast`, `less`, `greater`, and `gateway` are also available for common filtering needs. As an example, `tcp dst port 22` retains only TCP packets destined for port 22, 
while `ether host 00:0c:29:57:b3:ff or broadcast` captures traffic to or from a specific MAC address alongside all broadcast frames.

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/DisplayFilters.png)

Display filters operate on packets that have already been captured. Rather than discarding traffic, they control which packets are visible in the Packet List Pane at a given moment, 
leaving the underlying capture intact. This makes them more flexible during exploratory analysis, since the filter can be changed at any point without losing data. Display filters use 
a higher-level logical syntax built around protocol-typed field names. Fields are referenced by dot-separated identifiers such as `ip.addr`, `eth.addr`, `tcp.port`, `arp.opcode`, or 
`smb2.filename`, and compared using operators including `==`, `!=`, `>`, `<`, `>=`, `<=`, `contains`, and `matches`. Expressions can be combined with `and`, `or`, `xor`, and `not`, 
and grouped with parentheses. The slice operator `[ ]` allows matching against a specific byte range within a field.

Constructing display filters does not require memorising field names. Selecting any field in the Packet Details Pane causes its full identifier to appear in the status bar at the bottom 
left of the interface. Right-clicking the same field offers the options "Apply as Filter" and "Prepare as Filter", which insert the corresponding expression directly into the filter bar. 
This interactive approach is reliable for building correct expressions quickly, particularly when working with unfamiliar protocols. A few representative examples illustrate the syntax: 
`ip.addr == 1.2.3.4` matches all traffic to or from a given IP address, `arp.opcode == 1` isolates ARP requests, and `tcp.port == 80` selects packets where either the source or destination 
port is 80.

Capture filters and display filters do not share a syntax and cannot be used interchangeably. Applying a Berkeley Packet Filter expression in the 
display filter bar, or vice versa, will produce an error. When in doubt, display filters are the safer default: they preserve the full capture and can be adjusted at any time.

### 3.1.3 Dissectors

When Wireshark captures a packet, it does not simply store the raw bytes: it passes them through a chain of dissectors, each responsible for interpreting one layer of the 
protocol stack and rendering its fields as human-readable entries in the Packet Details Pane. Dissectors are modular components, and Wireshark ships with several hundred of 
them covering the most common protocols in use.

The chain always begins with the Frame dissector, which does not decode a protocol in the conventional sense but attaches capture-level metadata to the packet: its number in 
the sequence, the timestamp recorded at capture time, the interface on which it arrived, and the relationship between the captured length and the original length on the wire. 
From there, Wireshark hands the remaining bytes to the appropriate Layer 2 dissector, typically Ethernet, which in turn identifies the next-layer protocol and passes control 
accordingly. This process continues up the stack through the network and transport layers until the payload is either fully decoded by an application-layer dissector or left 
as raw data if no suitable dissector is available.

Wireshark selects dissectors primarily on the basis of port numbers. This works reliably for traffic that follows convention, but creates problems when services run on non-standard ports. 
HTTP traffic arriving on port 1080, for instance, will be handed to the SOCKS dissector, since port 1080 is the registered port for that protocol. The resulting interpretation will be 
incorrect, the fields displayed in the Packet Details Pane will not correspond to the actual structure of the payload, and any display filters referencing HTTP-specific field names will 
fail to match. The same issue arises in offensive or misconfigured environments where services deliberately avoid their standard ports.

In such cases, Wireshark provides a manual override through the Decode As dialogue, accessible via Analyze → Decode As. This allows the analyst to instruct Wireshark to apply a specific 
dissector to traffic on a given port, regardless of the default association. The change takes effect immediately and updates both the Packet Details Pane and the filter engine. Verifying 
that the correct dissector is active before drawing conclusions from a capture is a necessary step, particularly when traffic does not behave as expected or when filter expressions return
no results despite packets being visibly present.

### 3.1.4 Understanding Network Traffic in Wireshark

The Packet Details Pane exposes the full layer-by-layer structure of every captured frame. Each layer corresponds to a subtree in the interface, 
containing the fields relevant to that protocol.

| OSI Layer | Wireshark Subtree | Key Fields |
|---|---|---|
| Layer 2, Data Link | Ethernet II | Source MAC, destination MAC |
| Layer 3, Network | Internet Protocol | Source IP, destination IP, TTL, fragmentation flags |
| Layer 4, Transport | TCP or UDP | Source port, destination port, flags, sequence and acknowledgement numbers (TCP only) |
| Layer 7, Application | HTTP, DNS, FTP, SMB, and others | Protocol-specific fields |

One behaviour worth understanding early is that MAC addresses are local to each network segment. A router replaces the source and destination MAC addresses at every hop, 
so the addresses visible in a capture reflect only the last link traversed, not the original sender or the final destination. IP addresses, by contrast, remain unchanged 
from source to destination across the entire path, unless the traffic passes through a device performing network address translation.

**TCP and UDP**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkTCPUDP.png)
**Illustration idea: a Wireshark screenshot showing a TCP three-way handshake in the Packet List Pane, with the SYN, SYN-ACK, and ACK packets clearly visible in sequence, and 
the Packet Details Pane open on the TCP flags subtree.**

TCP and UDP are the two transport-layer protocols an analyst encounters most frequently, and their behaviour in a capture differs in ways that are immediately visible.

TCP is connection-oriented. Before any application data is exchanged, the two endpoints complete a three-way handshake: the initiating host sends a SYN packet, 
the responding host replies with a SYN-ACK, and the initiator confirms with an ACK. This sequence is consistently visible in the Packet List Pane and serves as a 
reliable marker for the start of a TCP session. Throughout the session, individual packets carry flags that describe their role: SYN initiates, ACK acknowledges, 
PSH requests immediate delivery to the application, FIN signals an orderly close, and RST terminates the connection abruptly. An RST in a capture typically indicates 
that a port was closed, that a connection was refused, or that one side encountered an unrecoverable error.

UDP carries none of this machinery. There is no handshake, no acknowledgement, and no built-in mechanism for retransmission. A UDP exchange appears in the capture as one 
or more datagrams sent without any prior negotiation, which makes it well suited to latency-sensitive applications such as DNS, DHCP, and streaming media, but means that 
loss or reordering is invisible at the transport layer.

**ARP**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkARP.png)
**Illustration idea: a Wireshark screenshot showing an ARP request broadcast followed by a unicast ARP reply, with the Info column displaying the "Who has" and "is at" 
strings, and the Ethernet II subtree open to show the broadcast destination address.**

The Address Resolution Protocol maps IP addresses to MAC addresses within a local network segment. Normal ARP operation follows a two-step exchange: a host that needs to reach an 
IP address it does not yet have a MAC address for sends a broadcast frame asking "Who has IP x.x.x.x?", and the host holding that address replies directly with 
"IP x.x.x.x is at MAC aa:bb:cc:dd:ee:ff". Applying the display filter `arp` isolates all ARP frames in the capture and makes this exchange straightforward to follow.

A gratuitous ARP is an ARP reply sent by a host without having received a request. It announces an IP-to-MAC mapping to the local segment unprompted. This occurs legitimately when 
a host comes online after a reboot or during a failover event, but the same mechanism can be exploited to poison the ARP caches of other hosts on the segment. ARP includes no 
authentication: any host can send a reply, solicited or not, and other hosts will generally accept it and update their cache accordingly.

**DNS**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkDNS.png)
**Illustration idea: a Wireshark screenshot showing a DNS query and its response in the Packet List Pane, with the Info column displaying the queried domain name and 
resolved IP address, and the DNS subtree expanded in the Packet Details Pane to show the answer section.**

DNS resolution appears in a capture as a pair of UDP datagrams on port 53: a query from the client naming the domain it wishes to resolve, and a response from the 
server containing the corresponding IP address. The Info column in the Packet List Pane renders both the queried name and the returned address directly, making DNS exchanges 
readable without opening the Packet Details Pane. The display filter `dns` isolates all DNS traffic, both queries and responses.

TCP is used on port 53 when a response is too large to fit in a single UDP datagram, and for zone transfers between DNS servers. Seeing TCP port 53 traffic in a capture from a workstation 
is therefore worth noting, as it is uncommon in normal client operation.

**Port numbers and protocol identification**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkPortNumbers.png)
**Illustration idea: a Wireshark screenshot of a mixed capture showing several protocols in the Protocol column (DNS, HTTP, TCP, ARP), illustrating how Wireshark labels 
traffic automatically based on port numbers, with one row selected to show the port fields in the TCP subtree.**

Wireshark uses port numbers as the primary signal for selecting a dissector and labelling traffic in the Protocol column. Port 80 is labelled HTTP, port 443 HTTPS, port 53 DNS, 
and port 21 FTP, among others. Port numbers fall into three ranges: well-known ports from 0 to 1023, registered ports from 1024 to 49151, and dynamic or ephemeral ports from 49152 upward. 
Client applications typically use a port drawn from the dynamic range as their source port for each new connection, which is why outbound traffic commonly shows a high-numbered source 
port paired with a well-known destination port.

This automatic resolution is convenient but not infallible. A service listening on a non-standard port will cause Wireshark to apply whichever dissector is registered for that port by 
default, which may produce an incorrect interpretation. As discussed in section 3.1.3, the Decode As dialogue provides the means to correct this when the actual protocol is known.

### 3.1.5 Reading Attack Traffic in Wireshark

When faced with an unfamiliar capture, a reliable starting point is to identify the protocol using the Protocol column, read the one-line summary in the Info column, 
and then descend into the Packet Details Pane layer by layer. The Follow TCP Stream function reconstructs full conversations from individual packets, and the Expert 
Information dialogue surfaces anomalies that Wireshark has flagged automatically, including duplicate addresses, retransmissions, and malformed headers.

**ARP Spoofing and Poisoning**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkARPSpoofing.png)

ARP spoofing exploits the absence of authentication in the Address Resolution Protocol. The characteristic sign in a capture is multiple ARP replies associating different MAC 
addresses with the same IP address. A legitimate host does not send unsolicited ARP replies, so a gratuitous ARP from an unexpected source warrants attention, particularly if 
it claims the MAC address of the default gateway. The practical consequence is that traffic intended for the gateway is redirected to the attacker's machine, meaning FTP, HTTP, 
and other application-layer packets will arrive at a MAC address that does not belong to the gateway.

Wireshark detects this automatically. Opening Analyze → Expert Information will surface a "duplicate IP address" warning when conflicting ARP mappings are observed in the capture. 
The display filter `arp` isolates all ARP frames and allows direct comparison of the MAC addresses appearing in successive replies for the same IP.

**DNS Spoofing**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkDNSSpoofing.png)

DNS spoofing manifests as a DNS reply that resolves a legitimate domain name to an IP address controlled by the attacker rather than the authoritative server. In a capture, this 
appears as a standard DNS response packet whose answer section contains an unexpected address. Applying the filter `dns` and examining the Info column allows comparison of returned 
addresses against known legitimate values.

A related vector involves a rogue DHCP server. By responding to DHCP discovery requests before the legitimate server does, an attacker can distribute a DNS server address under their 
control to clients on the segment. This is visible in a capture as multiple DHCP Offer packets in response to a single DHCP Discover, originating from different source MAC addresses.

**Port Scanning**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkPortScanning.png)

A port scan is one of the more straightforward attack patterns to identify in a capture. The defining characteristic is a rapid succession of TCP SYN packets sent from a single source 
to consecutive or pseudo-random destination ports on the same target host. The Time column makes the pace immediately apparent: a scan conducted with a tool such as nmap can generate 
hundreds of SYN packets within a single millisecond.

The responses reveal the state of each port. A closed port replies with RST/ACK, while an open port replies with SYN-ACK. In a typical SYN scan, the scanner sends a RST after receiving 
the SYN-ACK, deliberately avoiding the completion of the handshake to minimise its footprint. The display filter `tcp.flags.syn == 1 and tcp.flags.ack == 0` isolates the initial SYN 
packets and makes the scope of the scan visible at a glance.

**Denial of Service**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkDoS.png)

Denial of service attacks are generally identifiable by an abnormally high volume of packets of a single type originating from one or more sources over a short period. The specific 
pattern depends on the technique in use.

A SYN flood produces a large number of SYN packets with no corresponding ACK, causing the target to allocate state for connections that are never completed. An ICMP flood generates a 
sustained stream of Echo Request frames, visible with the filter `icmp`. A UDP flood sends high volumes of datagrams to various ports, prompting the target to reply with ICMP Destination 
Unreachable messages for each port that has no listening service.

Slowloris differs from the above in that it does not rely on volume. It holds HTTP connections open by sending partial requests at a slow rate, never completing them. This is difficult 
to detect by packet count alone. The indicator to look for is a set of TCP connections that remain open for an unusually long time without progressing to a complete HTTP exchange.

**Shells and Post-Exploitation Traffic**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkShells.png)

Once a host has been compromised, the attacker typically establishes a persistent communication channel. Two patterns are common. In a bind shell scenario, the compromised machine opens 
a listening port, and the attacker connects to it from outside. This appears in a capture as an inbound TCP connection completing a full handshake toward an unusual port, such as 4444. 
In a reverse shell scenario, the compromised machine initiates the connection outward toward the attacker's infrastructure, producing outbound traffic to an external IP on a non-standard port.

The display filter `tcp.port == 4444`, adjusted to whatever port the payload uses, isolates the relevant stream. Right-clicking any packet in that stream and selecting Follow → TCP Stream 
reconstructs the full conversation as a readable sequence. In an unencrypted shell, this view may reveal commands and responses in plaintext, including strings associated with common 
frameworks such as metasploit or meterpreter, which may also appear directly in the Packet Bytes Pane.

When the shell is tunnelled over HTTPS, the traffic is encrypted and indistinguishable from legitimate web traffic at the packet level. In that case, the destination IP address is the 
only readily available indicator, and its value depends on threat intelligence rather than packet content.

**APT Beaconing**

![name](https://lattice-walker.github.io/CipherOps/courses/networks/3illustrations/WiresharkAPTBeaconing.png)

Advanced persistent threat activity often involves malware that periodically contacts a command-and-control server to receive instructions or exfiltrate data. In a capture, this manifests 
as repeated HTTP GET requests to the same external IP address at regular intervals, targeting unremarkable resource names such as `default.htm` or `h.gif`. The regularity of the timing is 
the primary indicator: connections spaced exactly 120 seconds apart, for instance, are unlikely to reflect normal user behaviour.

Additional signs include source ports that increment sequentially across successive connections, a pattern produced by some malware implementations, and repeated SYN packets to the same
destination with no returning SYN-ACK, which may indicate that the command-and-control server is unreachable or has been blocked. The filter `ip.dst == [suspicious IP]` combined with 
`http` isolates the relevant traffic and makes the timing pattern visible in the Time column.



## 3.2 tcpdump

tcpdump is a command-line packet capture tool that relies on the libpcap library to intercept and display network traffic. It requires no graphical interface, so it is well suited to server environments, automated capture pipelines, and remote sessions where installing a full protocol analyser is impractical.

tcpdump shares the Berkeley Packet Filter syntax with Wireshark's capture filter engine, and it writes output to the pcap format, which Wireshark can read directly. This compatibility makes the two tools complementary: tcpdump handles collection in constrained environments, while Wireshark handles interactive analysis on a workstation.

### 3.2.1 Command-line usage

The basic invocation follows the form `tcpdump [options] [filter expression]`. The most frequently used options are:

- `-i` to specify the network interface,
- `-w` and `-r` to write captures to, or read them from, a pcap file,
- `-n` to suppress name resolution,
- `-v`, `-vv`, and `-vvv` to increase output verbosity,
- `-c` to stop after a given number of packets,
- `-s` to set the snapshot length.

When running without a `-w` flag, tcpdump prints a one-line summary for each packet to standard output. Each line contains the timestamp, protocol, source and destination addresses, TCP flags, and sequence numbers, in that order.

Filter expressions follow the Berkeley Packet Filter syntax. The following examples illustrate common patterns:

- `tcpdump -i eth0 -n tcp port 443` captures TLS traffic on a named interface while suppressing DNS lookups.
- `tcpdump -i any -w output.pcap host 192.168.1.1` records all traffic to and from a specific host and saves it to a file.
- `tcpdump -r output.pcap -n 'tcp and port 80'` reads a previously saved file and applies an additional filter for HTTP traffic.

### 3.2.2 Remote capture and integration with Wireshark

tcpdump can be combined with an SSH connection to capture traffic on a remote host and stream it in real time to a local Wireshark instance. The following pipeline achieves this:

```
ssh user@host tcpdump -i eth0 -w - | wireshark -k -i -
```

Here, the `-w -` flag instructs tcpdump to write pcap data to standard output rather than a file. The pipe forwards that stream to Wireshark, which the `-k -i -` flags instruct to begin capturing immediately from standard input. This approach is applicable to headless servers, embedded devices, and network appliances where running a graphical tool directly is not possible.


## 3.3 Scapy

Scapy is a Python-based packet manipulation library and interactive shell. It supports packet crafting, capture, injection, decoding, and pcap file handling within a single programmable environment. Where tcpdump and Wireshark are designed for passive capture and inspection, Scapy is oriented toward programmatic analysis and custom protocol testing, and can replace or complement either tool depending on the task.

### 3.3.1 Frame analysis with Scapy

Scapy reads pcap files through the `rdpcap()` function, which returns a list of packet objects that can be iterated over directly. Each packet object exposes its structure through two methods: `.summary()` prints a compact one-line description, while `.show()` displays the full layer-by-layer breakdown with all field values.

Individual layers are accessed by indexing the packet with the corresponding protocol class, for example `pkt[IP]` or `pkt[TCP]`. Fields within a layer are then accessible as attributes: `pkt[IP].src` returns the source address, `pkt[TCP].flags` returns the TCP control bits, and `pkt[DNS].qd.qname` returns the queried name in a DNS packet. Filtering across a capture is typically done with list comprehensions, allowing conditional selection based on any combination of layer presence and field value.

### 3.3.2 Packet crafting with Scapy

Scapy constructs packets by stacking protocol layers with the `/` operator. A complete Ethernet frame carrying a TCP segment, for instance, is expressed as `Ether() / IP() / TCP() / Raw()`. Each layer is initialised with default values that Scapy computes automatically, such as checksums and length fields, but any field can be overridden explicitly, including source and destination addresses, the IP time-to-live, TCP flags, and the raw payload.

Transmission is handled by a set of functions distinguished by the layer at which they operate. `send()` transmits at layer 3, leaving Ethernet framing to the operating system, while `sendp()` transmits at layer 2 with full control over the Ethernet header. The `sr()` and `srp()` counterparts combine transmission with reception, returning matched request-response pairs and any unanswered packets.

Common crafting tasks include:

- constructing a TCP SYN packet directed at a specific port,
- sending a gratuitous ARP frame to update neighbour caches,
- assembling a custom DNS query with a chosen record type and name.

### 3.3.3 Offensive and diagnostic use cases

Scapy is frequently used in laboratory settings to reproduce attack traffic for analysis. ARP spoofing frames, SYN flood sequences, and deliberately malformed packets can all be constructed and transmitted with precise control over every field, making it possible to study how a target system or protocol implementation responds to each case.

For protocol testing, Scapy supports fuzzing by allowing field values to be replaced with random or boundary-condition data before transmission. This makes it possible to probe implementations for handling of unexpected input without requiring a dedicated fuzzing framework.

Crafted or modified packets can be written to pcap files using `wrpcap()`, which produces output in the standard format readable by Wireshark and tcpdump. This allows a workflow in which packets are generated or transformed programmatically in Scapy and then examined interactively in Wireshark.
