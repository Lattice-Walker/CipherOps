#  IPv6 and Transition

## 1 IPv4 vs IPv6

The 32-bit address space of IPv4 provides approximately 4.3 billion unique addresses. This pool was exhausted at the level of the Internet Assigned Numbers Authority in February 2011, with most regional internet registries reaching exhaustion of their own remaining allocations within the following years.

Network Address Translation extended the usable life of IPv4 by allowing multiple devices to share a single public address. This approach introduced additional complexity into network design, broke the end-to-end connectivity model on which the original internet architecture was based, and complicated the operation of certain protocols. Network Address Translation specifically complicates peer-to-peer applications, voice over IP, and IPsec, since these protocols depend on assumptions about address consistency or embed address information within their payloads. Because Network Address Translation requires devices to maintain state for each translated connection, these devices also become potential single points of failure.

IPv6 uses 128-bit addresses, providing approximately 3.4 × 10³⁸ unique addresses. This address space was designed to remove address scarcity as a constraint on network growth.

IPv6 also introduces a fixed 40-byte header, replacing the variable-length header used in IPv4, with the stated aim of improving forwarding efficiency at routers. The header checksum present in IPv4 was removed from IPv6, reducing per-hop processing on the assumption that checksums implemented at the link layer and transport layer provide sufficient error detection.

IPv6 includes native support for address autoconfiguration through Stateless Address Autoconfiguration, which allows a device to construct its own address without requiring a DHCP server. IPv6 also replaces broadcast with multicast for network functions that previously relied on broadcast in IPv4, with the intention of reducing unnecessary traffic delivered to devices not involved in a given function.

Despite the exhaustion of the IPv4 address pool, deployment of IPv6 has proceeded gradually. As of the mid-2020s, IPv6 accounts for approximately 40 to 45 percent of user traffic measured by Google globally, with substantial variation between countries.

### 1.1 IPv6 Format and Header Fields

The IPv6 header has a fixed length of 40 bytes, in contrast to the variable 20 to 60 byte length of the IPv4 header.

![Header](https://lattice-walker.github.io/CipherOps/courses/networks/6illustrations/6Header.svg)

- The Version field is 4 bits and is set to the value 6.
- The Traffic Class field is 8 bits and serves the same purpose as the combined Differentiated Services Code Point and Explicit Congestion Notification fields in IPv4, used for Quality of Service marking.
- The Flow Label field is 20 bits and is intended to identify packets belonging to the same flow so that they receive consistent treatment, with use cases including equal-cost multipath hashing and Quality of Service processing.
- The Payload Length field is 16 bits and indicates the length of the data following the fixed header.
- The Next Header field is 8 bits and identifies the type of the header that follows, whether an extension header or an upper-layer protocol, replacing the function of the Protocol field in IPv4.
- The Hop Limit field is 8 bits and serves the same function as the Time to Live field in IPv4, being decremented by each router that forwards the packet. The Source Address and Destination Address fields are each 128 bits.

IPv6 supports extension headers, which are optional headers chained together through the Next Header field. Extension headers are used for functions including routing, fragmentation, authentication, encapsulating security payload, and hop-by-hop options.

Fragmentation in IPv6 is handled differently from IPv4: only the originating host may fragment a packet, and routers along the path do not perform fragmentation. As a consequence, Path MTU Discovery is required for a source host to determine the appropriate packet size before transmission.

Among the defined extension headers, the Hop-by-Hop Options header is the only one that must be processed by every router along the path. Because processing this header at every hop affects forwarding performance, its use is generally limited to specific circumstances.

Relative to IPv4, IPv6 removes the header checksum, the options field, and the Internet Header Length field, while adding the Flow Label field and moving all fragmentation responsibility to the source host.

### 1.2 IPv6 Addressing

An IPv6 address is written as eight groups of four hexadecimal digits separated by colons. Consecutive groups consisting entirely of zeros may be replaced with a double colon, though this abbreviation may be used at most once within a single address to avoid ambiguity.

An IPv6 address is 128 bits in length and is typically divided into a 64-bit network prefix and a 64-bit interface identifier.

IPv6 defines three categories of address. 
- A unicast address identifies a single interface and includes global unicast addresses, link-local addresses, and unique local addresses.
- A multicast address identifies a group of interfaces, with a packet sent to a multicast address delivered to every interface belonging to that group, replacing the function of broadcast.
- An anycast address is assigned to multiple interfaces, with a packet sent to that address delivered to the interface considered nearest according to the routing protocol's metrics. IPv6 does not define a broadcast address type; functions previously served by broadcast in IPv4 are instead handled through specific multicast groups.

Global unicast addresses are routable on the public internet and are currently allocated from the 2000::/3 prefix block. Link-local addresses are automatically configured on every IPv6-enabled interface, using the fe80::/10 prefix, and are used for functions including neighbour discovery and routing protocol communication; they are not routable beyond the local link. Unique local addresses use the fc00::/7 prefix and are broadly analogous to the private address ranges defined for IPv4, being routable within a site but not on the public internet.

The interface identifier portion of an address can be derived from a device's MAC address using the EUI-64 process, generated randomly for privacy purposes, or assigned manually by an administrator. Privacy extensions, defined in RFC 4941, generate temporary, randomised interface identifiers in order to prevent a device from being tracked across networks based on a stable, hardware-derived address.

The Neighbour Discovery Protocol replaces the Address Resolution Protocol used in IPv4. It uses ICMPv6 messages to perform address resolution, router discovery, and duplicate address detection.

Routers advertise network prefixes to hosts through Router Advertisement messages, which enable Stateless Address Autoconfiguration. DHCPv6 provides an alternative, stateful method of address assignment and option distribution, and can be used either alongside or instead of Stateless Address Autoconfiguration depending on the requirements of a given deployment.

The standard allocation unit for a local area network segment is a /64 prefix, regardless of the number of hosts expected on that segment. Larger prefixes are used for other purposes: a /127 prefix, recommended by RFC 6164, is used for point-to-point links, and a /128 prefix is used for loopback addresses.

### 1.3 IPsec in IPv6

IPsec was originally developed alongside IPv6 and was designated mandatory to implement in early IPv6 specifications. RFC 6434, published in 2011, downgraded this requirement to a recommendation, bringing IPv6 practice into alignment with IPv4, where IPsec support had always been optional.

In IPv6, IPsec is integrated through two extension headers rather than through separate encapsulation. The Authentication Header provides integrity and origin authentication for an IP packet but does not provide confidentiality, and is identified by Next Header value 51. The Encapsulating Security Payload header provides confidentiality, integrity, and optional authentication, and is identified by Next Header value 50.

IPsec can operate in two modes. In transport mode, only the payload of the IP packet is protected, and the original IP header remains visible. In tunnel mode, the entire original packet is encapsulated within a new IP packet, a mode commonly used for virtual private networks and for protection between gateways.

Internet Key Exchange version 2 is the standard protocol used to negotiate IPsec security associations and supports IPv6 natively.

In practice, end-to-end IPsec between arbitrary hosts remains uncommon. IPsec is more widely deployed at the gateway level, for the purpose of establishing virtual private networks between sites.

IPsec in transport mode is incompatible with Network Address Translation, since Network Address Translation modifies IP headers that transport mode does not protect against alteration. NAT Traversal addresses this by encapsulating the Encapsulating Security Payload within a UDP header. This workaround is less relevant in IPv6 environments, where Network Address Translation is not expected to be present given the size of the available address space.

### 1.4 IPv6 Routing

Several routing protocols have been extended or adapted to support IPv6. 
- OSPFv3, defined in RFC 5340, extends OSPF to support IPv6 prefixes, runs directly over IPv6, and supports multiple address families within a single implementation.
- IS-IS has been extended for IPv6 through additional type-length-value structures that carry IPv6 reachability information, allowing a single IS-IS process to handle both IPv4 and IPv6 simultaneously.
- RIPng, defined in RFC 2080, is a simple distance-vector protocol for IPv6, limited to small networks by the same 15-hop diameter constraint that applies to RIP for IPv4. BGP-4 supports IPv6 through the Multiprotocol BGP extensions defined in RFC 4760, which allow a single BGP session to carry both IPv4 and IPv6 Network Layer Reachability Information.

Static routing is fully supported in IPv6, with link-local addresses commonly used as next-hop addresses for static routes configured on point-to-point links.

The large IPv6 address space and its hierarchical allocation policy were designed to facilitate route aggregation and limit the growth of global routing tables. In practice, the global IPv6 BGP table has grown alongside the IPv4 table, since multihoming arrangements and traffic engineering practices lead to the deaggregation of address blocks that would otherwise be aggregated.

Router Advertisement messages, part of the Neighbour Discovery Protocol, carry both prefix information and default gateway information, removing the need for a separate default gateway configuration step on hosts. Router Advertisement messages can also carry recursive DNS server information through the RDNSS option, defined in RFC 8106, reducing the need for DHCPv6 in networks where only basic host configuration is required.

### 1.5 Persistent Vulnerabilities in IPv6

The Neighbour Discovery Protocol does not include built-in authentication, making it susceptible to neighbour cache poisoning, a form of attack analogous to ARP spoofing in IPv4.

An attacker can send unsolicited Router Advertisement messages to redirect traffic or cause denial of service, a class of attack referred to as rogue Router Advertisements. This is mitigated by RA Guard, defined in RFC 6105, which allows network devices to filter unauthorised Router Advertisement messages.

Secure Neighbour Discovery, defined in RFC 3971, addresses the underlying authentication gap by using cryptographically generated addresses and RSA signatures to authenticate Neighbour Discovery Protocol messages. It is rarely deployed in practice, owing to the complexity of its implementation and operation.

Extension header chains can be constructed in ways that evade firewalls and intrusion detection systems that do not fully parse all extension headers present in a packet. Some implementations respond to this risk by dropping packets containing unusual or excessive extension header combinations.

Because only the source host fragments packets in IPv6, intermediate devices do not perform reassembly. Overlapping fragment attacks and tiny fragment attacks nonetheless remain possible and can be used to bypass security controls that do not correctly handle fragmented IPv6 traffic.

Certain multicast groups in IPv6 are reachable by all nodes on a link. An attacker with access to the local link can exploit this to generate a disproportionate volume of traffic by addressing packets to these groups.

The transition mechanisms used to support coexistence between IPv4 and IPv6 introduce additional attack surface. Automatic tunnelling mechanisms such as 6to4 and Teredo encapsulate IPv6 traffic within IPv4, which can allow this traffic to bypass perimeter security controls that are not configured to inspect encapsulated payloads. Dual-stack hosts, running both IPv4 and IPv6 simultaneously, may be reachable over IPv6 even where an organisation's security policy was designed with only IPv4 in mind. Firewalls and intrusion detection systems that do not inspect IPv6 traffic may pass it without applying any policy at all.

The size of the IPv6 address space makes random scanning of an entire subnet impractical. Attackers can instead target predictable or well-known addresses, such as router link-local addresses or anycast addresses, and may use DNS records or other discovery methods to enumerate active hosts.

Privacy extensions reduce the ability to track a device over time using a stable address, but they do not prevent an attacker already present on the local network from observing traffic directly.
